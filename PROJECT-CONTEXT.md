# Проект: система бронирования кортов — контекст

Документ описывает, что это за продукт, из чего он состоит и какие решения
переделывать не надо. Технические детали запуска — в `README.md`.

## Модель проекта

Подписочная платформа-экосистема. Разового внедрения нет: подключение клуба
бесплатное, вся выручка — ежемесячная подписка по одному из трёх тарифов:

| Тариф | Цена | Что открывает |
|---|---|---|
| **Броні** | 1 000 грн/мес | Запись, сетка дня, клиенты, абонементы, онлайн-оплата |
| **Команда** | 1 500 грн/мес | + тренеры, группы, турниры, открытая игра |
| **Аналітика** | 2 500 грн/мес | + Pro-аналитика, Telegram-боты, напоминания, лист ожидания, дайджест, нейроменеджер для игроков и нейроаналитик для владельца (Gemini) |

Почему так, а не «установка + хостинг»: разовый чек за внедрение — главный
барьер на первом разговоре, и он же делает продукт похожим на заказную
разработку, а не на платформу. Подписка без входного билета снимает этот
барьер, а цена тарифа отражает ценность — 1 000 грн это две-три часа корта
в месяц, тогда как система закрывает неявки и ручную запись каждый день.
Экосистема — потому что в одной системе живут клуб, его персонал, игроки,
Telegram-боты и сеть точек, и ценность растёт с каждым подключённым клубом
(открытые игры, профиль игрока в нескольких клубах).

Тарифы живут в системе (`Plan`, `ClubInvoice`, `lib/plans.ts`) и закрывают
платные возможности флагами `trainers` / `groups` / `analytics` / `telegram`.
Цены — в таблице `Plan`, редактируются в платформенной админке без деплоя;
стартовый каталог — `scripts/plans-init.ts`. Инструменты цены: пробный период
и индивидуальная цена клубу (`planPrice`).

## Стек

Бек: Node + TypeScript + Express + Prisma + PostgreSQL + Zod + Luxon.
Фронт: React + Vite, без Tailwind и без UI-библиотек — виджет ставится на чужие
сайты, и чужой CSS туда попадать не должен.

Зависимостей намеренно мало. Всё, что можно написать за сотню строк вместо
мегабайта в `node_modules`, написано: генератор `.xlsx` поверх `zlib`, графики
inline-SVG, состояние — Zustand.

## Состав

Два приложения в одном репозитории:

- `court-booking-api` — бекенд и Telegram-боты;
- `court-booking-web` — кабинет клуба, публичная страница клуба и встраиваемый
  виджет (`npm run build:widget` собирает его одним файлом).

## Что сделано

Масштаб: **34 модели** в схеме, **62 миграции**, **~107 эндпоинтов**,
**62 тестовых файла** на беке и **57** на фронте.

**Бронирование.** Сетка слотов, рабочие часы клуба, блокировки, перенос брони
(`BookingReschedule`), лист ожидания (`WaitlistEntry`), правила отмены и
дедлайн записи.

**Групповые занятия.** Бронь-контейнер + места в ней (`BookingSeat`): у места
свой статус, своя цена и своя оплата.

**Оплаты.** LiqPay и Monobank (`lib/payments/`), плюс `mock` и `demo` для
разработки. Предоплата настраивается на клуб: выключена, обязательна или на
выбор игрока. Возвраты, сверка смены (`ShiftClose`), взаиморасчёты
(`settlements`), журнал начислений (`BookingLedgerEntry`).

**Клиенты.** Карточка по телефону (E.164), абонементы (`Pass`, `PassPlan`,
`PassUsage`), бонусы и скидки, метки клуба, чёрный список, требование
предоплаты, дни рождения, кабинет игрока с паролем.

**Персонал.** Тренеры с расписанием и исключениями, роли (владелец / модератор /
тренер), смены сотрудников (`StaffShift`, `StaffHours`), журнал изменений
(`ChangeLog`), заметки и отзывы по любой сущности (`Note`).

**Продажи и склад.** Акции (`Promo`), инвентарь и прокат (`InventoryItem`,
`BookingRental`), расходы клуба (`ClubExpense`).

**Telegram.** Бот клуба и бот игрока: привязка номера, напоминания, дайджест,
аналитика, подтверждение «приду», Mini App.

**Аналитика и отчёты.** Разложена на разделы (Обзор / Выручка / Загрузка /
Клиенты / Тренеры / Экипировка). Главные цифры, выводы с конкретным действием,
графики загрузки и спроса, сегменты клиентов, прогноз, глоссарий терминов.
Произвольный период с шагом «раньше — позже».

**Выгрузка картотеки.** `.xlsx` (собственный генератор, `lib/xlsx.ts`) и CSV,
только для владельца, каждая выгрузка пишется в `ChangeLog`.

**Источники трафика.** UTM-метки и переход снимаются на входе и доезжают до
брони; канал считает сервер (`lib/attribution.ts`). Первый контакт хранится в
карточке клиента, последний — в каждой брони.

**Платформа.** Мультиклубность: группы клубов (`ClubGroup`), переключение между
точками сети, платформенная админка (`routes/platform.ts`).

## Ключевые архитектурные решения (не переделывать без причины)

1. **Свободных слотов в базе нет.** Хранится только занятое — `Booking` и
   `Block`. Свободное вычисляется вычитанием из рабочих часов дня.
2. **Двойная бронь блокируется базой, а не кодом.** Перед записью нет проверки
   «свободно ли». Прилетает `23P01` → API отдаёт 409 → виджет перерисовывает
   сетку. Гонку за инвентарь ловит `FOR UPDATE` в `lib/rentalStore.ts`.
3. **Всё время в базе — `timestamptz` (UTC).** Рабочие часы — минуты от полуночи
   по локальному времени клуба, конвертация через Luxon от `Club.timezone`.
4. **`clubId` берётся из JWT, никогда из тела запроса.** Обновления идут через
   `updateMany({where: {id, clubId}})`, чужая запись даёт `count=0` → 404.
   База клиентов общая на всю платформу — разделение живёт только в этих
   условиях, и ослаблять их нельзя. Тонкое место: у `BookingSeat` своего
   `clubId` нет, фильтр идёт через `booking.clubId`.
5. **Стили виджета изолированы** через `all: initial` и префикс `cb-`;
   кабинет — через `ap-`.
6. **Занятые слоты видны** (штриховка), а не скрыты — игрок видит свободное днём.
7. **Статусные цвета не брендируются.** Клуб выбирает `--ap-brand`, но
   «Подтверждено» не становится вишнёвым: иначе оно сольётся с «Отменить».
8. **Канал трафика считает сервер, а не браузер.** Браузер шлёт факты (метки,
   переход), вывод делает API — иначе отчёт об окупаемости рекламы стал бы тем,
   что напишут в запросе.
9. **Отчёт не выдаёт отсутствие данных за ноль.** «Нет данных» и «ноль» —
   разные ответы; шкала процентов всегда 0–100, а не от максимума выборки.
10. **`ADMIN_STYLES` — шаблонный литерал.** Обратные кавычки внутри него
    обрывают строку посреди CSS, и кабинет падает с белым экраном.

## Что не сделано

- Отдельный срез по прокату в аналитике: раздел «Экипировка» есть, данных нет.
- Разбивка выручки по способу оплаты (наличные / терминал / онлайн) в отчётах.
- Когортный возврат новичков и список должников на главном экране аналитики.
- SMS, экспорт в Google Calendar.
- Полная CRM (зарплаты, склад, касса) — намеренно: там Appointer, Altegio и
  YCLIENTS с командами, соло-разработчик туда не заходит. Наша часть —
  бронирование, абонементы, напоминания и отчёты по ним.

## Решения по абонементам

- Регистрации клиента нет. Идентификатор — телефон, нормализованный к E.164.
- Телефон уникален внутри клуба, не глобально (один человек, два клуба).
- Имя из формы не перезаписывает карточку, исправленную админом.
- Каждое списание — запись `PassUsage`, откатывается одной кнопкой.
- Из нескольких активных абонементов берётся сгорающий раньше.
- Абонемент показывает админ в планшете, клиент ничего не предъявляет.
- QR-коды не делаем. Telegram — самообслуживание, не пропуск.

## Решения по сегментам клиентов

Сегмент считается сам, по дате последнего визита, и руками не меняется
(`lib/customerRoster.ts`). Границы — 30 и 90 дней, новичок — до 5 визитов.
Это не настройка клуба: сегмент должен означать одно и то же везде, иначе
разговор о цифрах между нами и клубом рассыпается. Метки клуба — отдельно,
их ставят руками.

## Как продаём

Персональная демо-ссылка с логотипом клуба → встреча → выбор тарифа → оплата
первого месяца. Скрипт разговора — в `COLD-CALL-SCRIPT.md`: чем пользуетесь
сейчас, сколько платите, какой тариф закрывает вашу боль. Три отказа на
вопросе об оплате первого месяца из пяти разговоров = ниша не подтвердилась.

Полный гайд — воронка, цены по трём уровням подписки, партнёрский канал через
обслуживающие клубы компании, критерии решений — в `ВОРОНКА-ПРОДАЖІВ.md`.

## Предпочтения по работе

Сразу готовые файлы и рабочий код, без теории. Деловые тексты — на украинском.
Комментарии в коде — на украинском, и объясняют «почему так», а не «что делает
строка».
