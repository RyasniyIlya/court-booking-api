# API: що зробити після цих правок

## Одна команда

З папки `court-booking-api`:

```
npm run db:migrate
```

Назвати `club_billing`. Prisma побачить нові поля й моделі та згенерує міграцію сама.

**Тільки `npm run db:migrate`, не `npx prisma migrate`.** `npx` тягне Prisma 7,
яка падає з P1012: там `url = env("DATABASE_URL")` у `datasource` більше не
підтримується. Це ж стосується MCP-плагіна Prisma — він ходить через `npx`
і на цьому проєкті не працює, перевірено.

Папку `prisma/migrations/<час>_club_billing/` **закомітити**: Render робить
тільки `migrate deploy`.

### Про enum і одну міграцію

Правило «значення enum і його використання — в РІЗНИХ міграціях» стосується
`ALTER TYPE ... ADD VALUE` до вже наявного enum. Тут створюються два **нові**
типи (`BillingPeriod`, `InvoiceStatus`) — це `CREATE TYPE`, і одна міграція
його витримує. Ділити не треба.

Потім, як завжди:

```
npm run build
```

## Що змінилось

### `prisma/schema.prisma`

У `Club`:

```prisma
paidUntil     DateTime?
billingPeriod BillingPeriod @default(MONTH)
billingNote   String?
invoices      ClubInvoice[]
```

Плюс `enum BillingPeriod`, `enum InvoiceStatus` і модель `ClubInvoice`.

**Модель навмисно не `Payment`.** Та вже зайнята платежами гравців за корти.
Сплутати їх означає одного дня показати клубу його виручку як наш борг.

### `src/lib/billing.ts` — новий

Єдине місце, де рахується стан обслуговування. `clubBilling(club, now)` віддає
`ok | due | grace | blocked`, дні до/після і `online`. Рішення, що саме
вимикати, ухвалюють роути — інакше логіка розповзеться і почне розходитись
між віджетом і кабінетом.

Константи: `GRACE_DAYS = 7`, `WARN_DAYS = 14`, `PERIOD_PRICE`.

Дні рахуються по календарних, через Luxon, а не діленням мілісекунд на
86 400 000: на переході на зимовий час доба 25 годин, і «лишилось 7 днів»
перетворилось би на 6.

### `src/routes/public.ts`

**`loadClub` більше не фільтрує `isActive`.** Раніше вимкнений клуб просто не
знаходився, і віджет показував «Розклад тимчасово недоступний» — тобто помилку.
Гравець не винен, що клуб забув заплатити.

- `GET /clubs/:slug` — при `blocked` віддає `online: false` плюс назву, телефон,
  адресу і бренд. Статус 200: для гравця це режим роботи, а не збій
- `GET .../availability` — `{ closed: true, offline: true, courts: [] }`
- `POST .../bookings` — `403 CLUB_OFFLINE`. Остання лінія: POST може прилетіти
  зі старої вкладки, відкритої до вимкнення

### `src/routes/admin.ts`

- Новий `GET /api/admin/billing` — стан, строк, ціни періодів, останні
  24 рахунки. `billingNote` назовні не віддається: це наші нотатки
- У `PATCH /club` додано `billingPeriod`

**Кабінет не блокується ніде.** У ньому лежать броні клубу — його робота і
його гроші. Забрати до них доступ за місячний борг непропорційно, і це саме
той крок, після якого пишуть у профільні чати. Вимикається лише онлайн-запис:
дзвінки повертаються на адміністратора, і мотивація заплатити виникає сама.

## Що лишилось поза системою

**Продовження проходить вручну.** Гроші приходять переказом, посиланням у
Telegram або готівкою, а `paidUntil` і `ClubInvoice.paidAt` проставляються
руками — поки що через Prisma Studio.

Це свідомо. Своє автосписання потребувало б еквайрингу на нашому боці, а ми
його не заводимо: гроші гравців ідуть на рахунок клубу напряму, і ставати
посередником у розрахунках заради підписки немає сенсу — посередник
зобовʼязаний бути фінустановою.

**Кнопка «Продовжити обслуговування»** в кабінеті показується, тільки якщо
в `AdminPanel` передати `contact`. Один рядок у `App.jsx`:

```jsx
<AdminPanel apiBase={API_BASE} contact="mailto:hello@example.com" />
```

Або `https://t.me/...` — що зручніше.

**Своєї адмінки з усіма клубами немає.** Для перших десяти достатньо таблиці
та `paidUntil` руками. Екран знадобиться клубі на пʼятнадцятому, і тоді вже
буде зрозуміло, що на ньому має бути.
