# Групові заняття

## Що це для клуба

У розкладі, крім звичайних броней корту, зʼявляються **групові заняття**:
«Ранкова йога», «Дитяча група 8–10», «Сквош для початківців». До заняття
можна підвʼязати тренера. Гравці записуються на вільні місця — кожен своїм
телефоном, але корт при цьому зайнятий один раз.

Тип обирається при створенні броні. **За замовчуванням — звичайна бронь**,
рівно та сама, що й до цього: нічого з наявного не змінюється, поки клуб сам
не поставить у розклад групове.

---

## Головне рішення: групове заняття — це `Booking` з місткістю

У базі стоїть `booking_no_overlap` (GiST EXCLUDE): дві активні броні не
перетинаються на одному корті. Це найцінніша гарантія схеми — саме вона
фізично не дає продати одну годину двічі.

Групові заняття б'ють у неї в лоб: вісім людей на одному корті об одній
годині.

Розглядали два шляхи:

**Окрема таблиця `GroupSession`.** Констрейнт між таблицями не працює — корт
довелось би займати «фантомною» бронню або покластись на перевірки в коді.
Плюс друга реалізація `busy` для розкладу і власна механіка серій.

**`Booking` з місткістю — обрано.** Групове заняття це ОДНА бронь корту, до
якої записуються люди; учасники лежать у дочірній таблиці. Констрейнт не
чіпаємо взагалі, розрахунок вільних слотів не міняється, серії
(`seriesId`, «щовівторка о 19:00») переиспользуються як є.

Ціна рішення одна: `customerName` стає nullable, бо в контейнера групи
немає одного клієнта.

Спершу здавалося, що це зачепить десятки місць. Перевірка показала інше —
більшість згадок `customerName` це ЗАПИС при створенні звичайної броні
(там завжди є валідоване імʼя) або zod-схема. Читань, які реально можуть
показати порожнечу, лише три:

| Місце | Стан |
|---|---|
| `web AdminBookingPanel.jsx:114` | вже `\|\| 'Без імені'` |
| `web AdminGrid.jsx:410, 465` | вже `\|\| 'Без імені'` |
| `web AdminPanel.jsx:207` | **не захищене** |
| `api lib/payments/apply.ts:108, 121` | **не захищені** (Telegram) |

Тобто робота тут — три рядки, а не аудит усього коду. Замість `|| 'Без імені'`
у групи має бути назва заняття, тому вводимо `bookingLabel(b)`:
`b.title ?? b.customerName ?? 'Без імені'` — і ставимо його в усі пʼять місць,
щоб група показувалась «Ранкова йога», а не «Без імені».

Компілятор тут НЕ помічник: `tsc --noEmit` після зміни схеми дав нуль
помилок — поле просто тече в JSON, і типи цього не ловлять. Перевіряти
довелось грепом, і саме тому список вище виписаний поіменно.

## Схема

```prisma
model Booking {
  customerName  String?   // було String — у групи клієнта немає
  customerPhone String?

  /// Групове заняття: скільки місць усього. null = звичайна бронь корту
  capacity     Int?
  /// Назва заняття для віджета: «Ранкова йога»
  title        String?
  /// Ціна одного місця, копійки
  pricePerSeat Int?

  seats BookingSeat[]
}

/// Одне місце в груповому занятті = один записаний гравець.
model BookingSeat {
  bookingId     String
  customerId    String?   // картка клієнта, як у звичайній броні
  customerName  String
  customerPhone String
  status        SeatStatus  // BOOKED | CANCELLED
  price         Int
  cancelToken   String @unique
}
```

Окремою ручною міграцією (у тому ж стилі, що `no_double_booking`):

```sql
-- Бронь або приватна, або групова. Третього не дано.
ALTER TABLE "Booking" ADD CONSTRAINT booking_private_or_group CHECK (
  ("capacity" IS NULL AND "customerName" IS NOT NULL)
  OR
  ("capacity" > 0 AND "title" IS NOT NULL)
);

-- Один телефон — одне місце. Частковий індекс, щоб скасоване місце
-- не заважало записатись знову.
CREATE UNIQUE INDEX seat_one_per_phone
  ON "BookingSeat" ("bookingId", "customerPhone")
  WHERE status = 'BOOKED';
```

### Останнє місце — єдине, що не закриває база

«Дітей не більше за `capacity`» декларативно в Postgres не виражається.
Тому запис у транзакції: `SELECT ... FOR UPDATE` на рядку броні, підрахунок
місць, вставка. Це єдине місце в проєкті, де захист від гонки лежить у коді,
а не в констрейнті — і саме тому воно має бути написане один раз і уважно.

## Фази

### Фаза 1 — фундамент (API)
1. ✅ Міграція написана: `20260824120000_group_sessions` — поля `Booking`,
   таблиця `BookingSeat`, CHECK + частковий індекс. **Ще не застосована.**
2. Запис у транзакції з `FOR UPDATE` — захист останнього місця
3. `bookingLabel()` у пʼять місць із таблиці вище

### Фаза 2 — кабінет створює групи
4. `AdminCreateDialog`: перемикач типу броні. **Типово — звичайна**;
   групова відкриває назву, кількість місць, ціну місця, вибір тренера
5. Сітка: комірка групи показує `Йога 3/8`, а не імʼя
6. Панель броні: список учасників; ресепшен додає й прибирає вручну —
   половина записів приходить телефоном, а не через віджет
7. Серії вже вміють «щовівторка» — окремої роботи не потребують

### Фаза 3 — віджет записує
8. `availability` віддає по зайнятому слоту `group: { title, capacity, taken, pricePerSeat, trainerName }`
9. Слот з групою малюється не як «зайнято», а як `Йога · 3/8 · 250 грн` і клікається
10. `POST /clubs/:slug/bookings/:id/join` — імʼя, телефон, коментар
11. Кабінет гравця показує записи в групи нарівні з бронями

### Фаза 4 — оплата за місце *(навмисно останньою)*
`Payment` зараз 1:1 з `Booking` (`bookingId @unique`). Оплата за місце
вимагає розвʼязати цю унікальність і правити вебхук. У першій версії групи
оплачуються **на місці** — інакше фаза 1 розтягнеться вдвічі заради того,
чого клуб ще не просив.

## Межі

Не робимо (поки ніхто не попросив):
- листи очікування на заповнену групу;
- абонементи саме на групові (є `Pass`, але звʼязок з місцями — окрема робота);
- тренер створює собі заняття сам. Тренер підвʼязується до заняття як
  ресурс; заводить групу власник або модератор. Права тренера на створення
  — окрема зміна в `lib/access.js`, і вона не потрібна, щоб запустити групи.
