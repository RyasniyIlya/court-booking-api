# Court Booking API

Мультиарендний бекенд системи бронювання кортів: броні, групові заняття,
оплати, абонементи, персонал, Telegram-боти й аналітика.

Node + TypeScript + Express + Prisma + PostgreSQL + Zod + Luxon.

Навіщо все це й чому саме так — у `PROJECT-CONTEXT.md`. Тут — як запустити і
де що лежить.

## Запуск

```bash
cp .env.example .env          # DATABASE_URL, JWT_SECRET і решта
npm install
npx prisma migrate deploy     # 62 міграції
npm run db:seed               # демо-клуб squash-arena
npm run dev                   # http://localhost:3000
```

Демо-вхід: `owner@squash.local` / `demo1234`.

Команди:

| Команда | Що робить |
|---|---|
| `npm run dev` | сервер у режимі watch |
| `npm run build` / `npm start` | збірка і запуск `dist/` |
| `npm test` | увесь набір (vitest) |
| `npm run db:migrate` | нова міграція в розробці |

| `npm run plans:init` | створити тарифні плани |
| `npm run security:preflight` | перевірка налаштувань перед деплоєм |

## Що вирішено і як

**Подвійна бронь.** Не перевіркою в коді, а обмеженням `EXCLUDE USING gist` у
Postgres. Два одночасні запити на 19:00 фізично не можуть обидва записатись:
другий отримує `23P01`, API повертає `409 SLOT_TAKEN`. Скасовані броні виведені
з-під обмеження — час звільняється.

**Гонка за інвентар.** Прокат резервується разом зі слотом, в одній
транзакції, під `FOR UPDATE` на позиціях (`lib/rentalStore.ts`). Інакше дві
броні забирали б останню ракетку.

**Сітка слотів.** Порожні слоти в БД не зберігаються. `lib/slots.ts` будує
масив із розкладу дня, кроку та зайнятих інтервалів. Логіка чиста й тестована —
`now` передається параметром.

**Таймзони.** У БД усе в `timestamptz`, тобто UTC. Робочі години зберігаються
як хвилини від опівночі за локальним часом клубу, конвертація — через Luxon від
`Club.timezone`. Перехід на зимовий час опрацьовано: 25.10.2026 у Києві о 03:00
два різні слоти з різним UTC.

**Ізоляція тенантів.** `clubId` береться з JWT, ніколи з тіла запиту. Адмінські
оновлення йдуть через `updateMany({where: {id, clubId}})` — чужий запис дає
`count = 0` і 404. Найтонше місце: у `BookingSeat` свого `clubId` немає, тому
фільтр іде через `booking.clubId`, і послабити його не можна.

**Захист від довільних інтервалів.** `isAlignedToGrid` не дасть створити бронь
на 20:37 чи поза робочими годинами, навіть якщо запит іде повз віджет.

**Можливості за тарифом.** Чотири прапорці: `trainers`, `groups`, `analytics`,
`telegram` (`lib/plans.ts`). Три з них закриває вартовий `requireFeature(...)`
на цілому роутері; `groups` перевіряється точково — `hasFeature(clubId,
'groups')` у створенні броні, бо груповим є не розділ, а окремий запис.

Пошук клієнта на ресепшені свідомо відкритий на всіх рівнях: інакше клуб
першого рівня не прийняв би бронь від постійного гравця — це вже не
«недоплатив за аналітику», а зламаний основний сценарій.

## Ендпоїнти

Повний перелік читається з коду — нижче орієнтир.

**Публічні** (CORS відкритий, віджет живе на чужому домені):
`GET /api/public/clubs/:slug`, `…/availability`, `POST …/bookings`,
`…/bookings/:id/join` (місце в груповому), `POST /api/public/bookings/:id/cancel`,
вхід і кабінет гравця, лист очікування.

**Адмінські** (`Authorization: Bearer <token>`): броні, корти, години, блоки,
тренери, персонал і зміни, клієнти й абонементи, акції, інвентар і прокат,
повернення, звірка зміни, налаштування клубу, Telegram, білінг.

**Аналітика** (`/api/admin/analytics/…`, OWNER та ADMIN, план `analytics`):
`summary`, `customers`, `customers/top`, `customers/:id/visits`,
`customers/export`, `trainers/load`, `trainers/popular`, `load`, `deep`,
`forecast`, `expenses`, `traffic`.

## Вивантаження картотеки

`GET /api/admin/analytics/customers/export?format=xlsx|csv` — **тільки OWNER**.

Решта аналітики це агрегати; тут інше — імена, телефони й email усіх клієнтів
одним файлом. Модератор працює з картками щодня, але поштучно, через пошук на
ресепшені; винести базу цілком — рішення власника. Кожне вивантаження пишеться
в `ChangeLog`.

`.xlsx` збирається власним модулем (`lib/xlsx.ts`) на `zlib`, без залежностей:
телефон лишається текстом, дата — датою, а другий аркуш пояснює, як читати
цифри. CSV лишається для розсилок і Google Таблиць.

## Джерело трафіку

UTM-мітки й домен переходу приходять у тілі броні, канал рахує сервер
(`lib/attribution.ts`). Канал у запиті ігнорується навмисно: інакше будь-хто
підписав би свою бронь «реклама».

- `Booking.trafficChannel` — останній дотик: що спрацювало на цю бронь.
- `Customer.firstChannel` — перший дотик: що привело людину в клуб. Пишеться
  рівно один раз.
- Посилання бота вже несуть мітку — інакше його записи зливалися б із прямими
  заходами.

Броні, створені до появи обліку, мають порожній канал і йдуть у звіті окремим
рядком «невідомо», а не розкидаються по каналах.

## Тест гонки

```bash
BODY='{"courtId":"<UUID>","start":"2026-08-20T16:00:00Z","end":"2026-08-20T17:00:00Z","customerName":"Тест","customerPhone":"+380671112233"}'
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST \
    -H 'Content-Type: application/json' -d "$BODY" \
    http://localhost:3000/api/public/clubs/squash-arena/bookings &
done; wait
```

Очікуваний результат: один `201`, решта `409`.
