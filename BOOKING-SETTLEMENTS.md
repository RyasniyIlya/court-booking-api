# Розрахунки за бронювання

Перед запуском оновленого API застосуйте міграції (`prisma migrate deploy`) та згенеруйте Prisma Client (`prisma generate`). Нова міграція: `20260908120000_booking_settlements`. Старі оплати та бонуси не вигадуються: історичні автори лишаються невідомими, початковий бонусний баланс — 0.

У налаштуваннях клубу → «Розрахунки на ресепшені» власник у режимі рівня 3 задає перелік кас/рахунків і дозволяє повернення готівкою, банківським способом або бонусами. Делегування повернень модераторам типово вимкнене. Всі працівники клубу можуть читати розрахунки; для внесення оплати потрібен PIN рівня 2. Тренер доступу до журналу не має.

У панелі приватної броні є журнал, сума отриманого/повернутого, залишок до оплати та бонусний баланс. Для групи розрахунки ведуться окремо за кожним місцем, включаючи скасовані місця. Ручна операція зберігає суму в копійках, спосіб, рахунок, причину/квитанцію, дату і знімок облікового запису співробітника. Повернення посилається на вихідну оплату; доступні часткові оплати й часткові повернення.

Готівка, термінал і переказ у новій формі — облік фактично отриманих/повернутих коштів. Форма не виконує банківський переказ. Наявний онлайн-еквайринг та повернення через провайдера працюють окремо: тільки власник, зі статусом за вебхуком. Онлайн-оплата враховується в залишку; ручний платіж заборонений, поки інвойс очікує оплати. Нові способи повернення застосовуються до ручних оплат; онлайн-оплату ця форма не конвертує в бонуси.

Бонусне повернення одразу зараховується клієнту цього клубу; 1 бонус = 1 грн (у БД — копійки). Цим балансом можна оплатити іншу бронь через модератора. Оплату бонусами можна повернути лише бонусами. Для бонусів потрібен прив'язаний клієнт. Повернення саме по собі не скасовує бронь: скасування часу — окрема дія.

Записи журналу не редагуються і не видаляються через API. `requestId` — UUID, унікальний у межах клубу; повтор після втрати мережі повертає ту саму операцію. Зміна payload під тим самим ключем відхиляється. Транзакція з блокуванням рядка клубу серіалізує перевірки залишків, записи та зміни бонусного балансу. Обмеження БД захищають позитивну суму, вид операції, спосіб та невід'ємний баланс. Додавання журналу не змінює старі аналітичні звіти на касові звіти.

API:

- `GET /api/admin/settlement-settings`, `PUT /api/admin/settlement-settings`.
- `GET /api/admin/bookings/:id/settlements`, `POST /api/admin/bookings/:id/settlements`.
- `GET /api/admin/seats/:id/settlements`, `POST /api/admin/seats/:id/settlements`.

POST: `{ requestId, kind: 'PAYMENT' | 'REFUND', method: 'CASH' | 'CARD' | 'TRANSFER' | 'BONUS', amount, account, note, originalId? }`. Для повернення потрібні `originalId` та непорожня причина `note`. Автор визначається сервером із сесії.

Перевірки: модульні/HTTP тести з підміненою БД покривають права, ізоляцію клубів, часткові оплати й повернення, баланс бонусів, ідемпотентність та налаштування. Для приймання на тестовій PostgreSQL застосуйте міграцію, одночасно надішліть два повернення понад залишок та переконайтеся, що записалося тільки одне; повторіть UUID після розриву з'єднання й перевірте незмінність балансу.
