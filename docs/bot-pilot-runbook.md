# Пілот Telegram-бота з одним клубом

Бот і масові розсилки (нагадування, черга очікування, дайджест, запрошення у відкриті ігри, «повернення загублених», сповіщення про броні) ще не перевірялися на реальних клієнтах. Цей документ описує, як запустити пілот безпечно: спочатку тільки на себе, потім на один клуб.

## 1. Запобіжник відправки

Усі вихідні повідомлення проходять через одну функцію `call()` у `src/lib/telegram.ts`. Рішення приймає `src/lib/telegramSafety.ts`.

| Змінна | Значення | Що робить |
| --- | --- | --- |
| `TELEGRAM_SEND_MODE` | `live` (або порожньо / не задано) | Поведінка як раніше, нічого не фільтрується. |
| | `allowlist` | Шле лише в чати з `TELEGRAM_ALLOWLIST_CHAT_IDS`; решту пропускає й рахує як `skipped`. |
| | `dry` | Нічого не шле в мережу. У лог іде лише хеш чату й назва шаблону. |
| `TELEGRAM_ALLOWLIST_CHAT_IDS` | `123456789,987654321` | Chat id через кому (пробіли ігноруються). Порожній список у режимі `allowlist` означає «нікому». |

Важливо:

- Невідоме значення `TELEGRAM_SEND_MODE` (одруківка на кшталт `allowlst`) вважається `dry`, а не `live`.
- Текст повідомлень у лог не потрапляє ніколи (там імена й телефони).
- Кожен масовий прохід пише один підсумковий рядок, якщо хоч щось відправляв або пропускав:
  `[telegram-summary] <шаблон> mode=<режим> sent=N skipped=N failed=N`.
  Шаблони: `digest`, `staff-reminder`, `player-reminder`, `waitlist`, `winback`, `open-match-invite`, `notify-booking`.
- У `dry` кожне пропущене повідомлення дає рядок `[telegram] dry sendMessage chat=<10 hex> template=<шаблон>`.
- Нагадування гравцям і «повернення загублених» у `dry` та `allowlist` (для чужих чатів) не ставлять мітку «нагадано» в базі. Після переходу на `live` ці люди отримають своє повідомлення. Побічний ефект: поки режим не `live`, ті самі записи проходять тік знову й знову, а в логах повторюються `skipped`. Для пілоту з одним клубом це нормально.
- Чат-команди (`/start`, `/today` тощо) працюють завжди; ліміт стосується того, куди бот пише, тож у `allowlist` бот відповість лише вашому чату.
- Керування вебхуком (`setWebhook`) запобіжником не обмежується.

Як дізнатися свій chat id: напишіть боту `/start`, у `dry`-логах видно лише хеш, тому беріть id з @userinfobot або з тіла вебхука в логах Render.

## 2. Підготовка до пілоту

1. Домовтеся з одним клубом. Завести на ньому тариф 3 (Telegram), створити тестового гравця із вашим Telegram.
2. На Render (сервіс API) задайте змінні:
   - `TELEGRAM_SEND_MODE=allowlist`
   - `TELEGRAM_ALLOWLIST_CHAT_IDS=<ваш chat id>[,chat id власника клубу]`
3. Перезапустіть сервіс. У логах має бути видно, що планувальники стартували.
4. Спочатку, якщо хочете перевірити тільки відбір одержувачів без відправки, виставте `dry`, дочекайтеся тіку й подивіться підсумкові рядки та `dry`-логи.

Пам'ятайте: планувальник нагадувань гравцям вимкнений поза production, доки не задано `PLAYER_SCHEDULER=on`. На проді він працює, тож із `allowlist` реальні клієнти клубу нічого не отримають.

## 3. Чекліст ручних сценаріїв

| № | Сценарій | Як перевірити | Очікуваний результат |
| --- | --- | --- | --- |
| 1 | `/start` | Напишіть боту `/start` з чату, не привʼязаного до клубу. | Бот показує вибір клубів (або головну вашого клубу, якщо ви вже гравець). Меню команд гостя. |
| 2 | Привʼязка | У кабінеті натисніть «Підключити Telegram» (код), або `/login пошта пароль`. | `Підключено до клубу <назва>`. Повідомлення з паролем видалене. Меню відповідає ролі. |
| 3 | Нагадування за 3 години | Створіть підтверджену бронь для тестового гравця з Telegram на час через ~170 хв (бронь старша за 30 хв). Дочекайтеся тіку (до хвилини). | Гравцю (вашому чату) приходить картка «Нагадування про гру» з кнопками «Прийду / Скасувати». Для броні через 190 хв нічого. У логах `[telegram-summary] player-reminder ... sent=1`. |
| 4 | Лист очікування | Зайняту годину заберіть у тестового клієнта (join waitlist), потім скасуйте чужу бронь. | Через тік приходить «Звільнився час, на який ви чекали» лише першому в черзі. Клуб не на тарифі 3 нікому не пише. |
| 5 | Запрошення у відкриту гру | Дайте тестовому гравцю згоду на маркетинг (`marketingConsentAt`), іншому без згоди. Створіть відкриту гру. | Запрошення приходить лише гравцеві з згодою й привʼязаним чатом. Гравцеві без згоди нічого. Підсумок `open-match-invite`. |
| 6 | Дайджест | Виставте `DIGEST_HOUR` на найближчу годину за часом клубу (локально, не на проді постійно). | Зведення приходить лише OWNER. ADMIN і тренер не отримують. |
| 7 | ADMIN відхилений | Увійдіть боту як ADMIN, надішліть `/today`, `/week`, `/revenue`, `/analytics`. | `Ця команда доступна власнику клубу.` / відмова. Жодних цифр виручки. |
| 8 | `/stop` | Гравцем надішліть `/stop`. | `Готово — більше нічого не надсилатиму.`; чат відвʼязаний, черга скасована, згода на акції скинута. Нагадування більше не приходять. |
| 9 | Екранування | Назвіть клуб, корт або клієнта `<b>Тест</b> & Co`. | Текст виводиться буквально, без жирного шрифту й без помилки Telegram `can't parse entities`. |
| 10 | Збій | Заблокуйте бота тестовим акаунтом і запустіть будь-яку розсилку. | У підсумку `failed=1`, решта одержувачів отримала повідомлення, сервіс не впав. |

Для кожного сценарію перевірте в логах рядок `[telegram-summary]` та відсутність помилок `[telegram] ... failed`.

## 4. Перехід на live

Робіть це лише після того, як усі пункти чекліста пройшли в `allowlist`.

1. Перегляньте логи пілоту за кілька днів: чи є `failed`, чи немає дублів.
2. Додайте в allowlist власника клубу, перевірте дайджест на ньому.
3. Змініть `TELEGRAM_SEND_MODE=live` (або приберіть змінну) і перезапустіть сервіс.
4. Перші дві години стежте за `[telegram-summary]`: `skipped` має бути 0, `failed` невеликим.
5. Щоб відкотитися, поверніть `allowlist` або `dry` і перезапустіть сервіс. Повідомлення, що вже пішли, повернути неможливо.

## 5. Автоматичні тести

`src/lib/botPilot.e2e.test.ts` проганяє ці сценарії через справжні обробники й планувальники з підміною лише бази й мережі (fetch). Запуск:

```
node node_modules/vitest/vitest.mjs run --pool=threads src/lib/botPilot.e2e.test.ts
```

## 6. Що тести не доводять

- Фактичну доставку, форматування HTML, кнопки й обмеження реального Telegram (ліміти, 429, блокування бота).
- Роботу вебхука та секрету, затримки мережі.
- Поведінку проти реальної бази (запити Prisma замінені підміною, умови `where` перевіряються лише в обсязі тесту).
- Часові зони й таймінг на реальному годиннику Render (тести передають `now` явно).
- Поведінку кількох інстансів сервісу одночасно.
- Тик «повернення загублених» (`winback`) і сповіщення про броні (`notify-booking`) покрито лише існуючими модульними тестами та шаром безпеки.
